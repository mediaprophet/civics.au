11 / Solid databox

A postbox between a program and a person.

If concession credentials are what a person holds, the databox is how a program and a person exchange things safely: a private, two-way postbox for each relationship—not a general-purpose wallet, and not a shared database.

Relationship-specific by design

The Solid Databox is a hypermedia communications service: a modern-day postbox operated for a declared program. Through it an organisation securely delivers records, receipts, credentials, warranty information and notices; the person returns submissions, corrections, claims, preferences or evidence. Every program relationship is a separate security domain—compartmentalised by design so that no single breach or authority collapses the whole picture of someone's life.

  • Isolated security domains: each program relationship is cryptographically separate.
  • Immutable records: accepted records are never silently overwritten—changes create linked, auditable events.
  • Portable connections: connection credentials are holder-bound, rotatable API keys, not platform logins.
  • Cryptographic receipts: every accepted submission produces a signed receipt the person keeps.

Built on open standards

The databox runs on W3C Solid-compatible personal data pods with Web Access Control—people hold their own data and grant scoped access, rather than organisations holding everyone's data in a central store. Authorisation composes pod policy with WAC/ACP rules; program URLs are opaque 128-bit identifiers carrying no customer information. Exchange is governed by an ODRL policy engine (versioned permission/prohibition/duty bundles), a deposit and submission gateway with shape validation and evidence quarantine, and an append-only evidence ledger with signed dispositions.

It is designed for the edge: the open-source Solid-CSS-Databox stack runs in a container on the kind of Linux edge controller described on the digital economy page—working at a community ground or local council without depending on a cloud provider.

Governance and consumer rights built in

Beyond transport, the databox carries the machinery of accountable exchange: role bindings and approval gates, resolution workflows, and verifiable-credential issuance/verification/revocation. Consumer-rights workflows are first-class—access requests, correction requests with field-level tracking, data portability with a portability registry, and an immutable ledger of all interactions. An MCP (Model Context Protocol) server API lets authorised tools and agents work against the same governed surface rather than a parallel private integration.

A module system, not a monolith

A dynamic module system (50+ industry modules in the reference build) lets a program enable only what it needs—POS and receipts, bookings, inventory, concessions and entitlements, consent and delegation, emergency access, loyalty, pricing, credentials, provenance—each declared with capabilities and routes. For the civics.au context, the concessions module is the obvious meeting point with the concession credentials work: entitlement management and programmable-grant settlement delivered through a governed, person-held postbox.

Where it fits the ecosystem

Community grounds need trustworthy plumbing between people and programs: site agreements, concession verification, project contribution records, repair histories, receipts. The databox supplies that plumbing as open infrastructure the person controls. On the cooperative projects page the same evidence-ledger pattern appears as the resource-commit record; on the infrastructure page it is the software layer running on the edge databoxes. Working demos and the Forge admin console are linked from the project site.

Status: open-source reference implementation with in-browser demos (synthetic data). Production deployment still requires hosting, governance agreements and security review appropriate to the data it will carry.
